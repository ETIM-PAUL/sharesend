# Deploying on Render

[`render.yaml`](../render.yaml) at the repo root describes everything: the agent service (Docker), the web app (Next.js) and Postgres, all in Singapore. Every push to `main` redeploys.

| Service | Runtime | What it is |
| --- | --- | --- |
| `sharesend-agent` | Docker (`Dockerfile`) | API, the eight autonomous jobs, the `baw` CLI. Has a 1 GB disk at `/root/.baw` for the Agentic Wallet session. |
| `sharesend-web` | Node (`web/`) | The Next.js app. |
| `sharesend-db` | Postgres 16 | The gift ledger. |

Use paid plans. A free web service sleeps, and the agent has to stay on to run its jobs and to hold a disk. A free Postgres expires. Check Render's pricing page for the current cost of the three instances and the disk.

## 1. Create it

1. Push this repo to GitHub (the Blueprint reads `render.yaml` from the branch).
2. In Render: **New > Blueprint**, pick the repo and branch `main`.
3. Render asks for every variable marked `sync: false`. Fill them in from your current Railway variables, with these exceptions:
   - `LIVE_TRADING`: enter `false` first. Switch to `true` only after step 3 below.
   - `AGENT_PUBLIC_URL`, `CLAIM_BASE_URL`, `WEB_ORIGINS`, `NEXT_PUBLIC_AGENT_URL`: these are the services' own URLs, which Render only assigns once they exist. Enter the likely ones, `https://sharesend-agent.onrender.com` and `https://sharesend-web.onrender.com`, then correct them in the dashboard if Render added a suffix. `NEXT_PUBLIC_AGENT_URL` is baked into the web build, so **redeploy the web service after changing it**.
   - `BINANCE_INSTANCE_ID`: keep the same value you use today. A new one signs the wallet out (you'll sign in again anyway on a new machine, step 3).
   - `ADMIN_TOKEN` is generated by Render. Copy it from the agent's environment tab into your local `.env` (the CLI reads it from there).

## 2. Moving off Railway: the database is the ledger

The vault's money is tracked in Postgres. Starting on an empty database while gifts are in flight would leave stock and USDT in the vault that nothing knows how to pay out. If any gift is unclaimed, paid or being bought, move the data:

1. **Stop the Railway agent from acting.** Set `JOBS=off` and `AUTO_EXECUTE=false` on it (or stop it), and wait for gifts in `BUYING` or `CLAIMING` to finish.
2. **Copy the database.** From your laptop, using each database's *external* connection string (never paste these anywhere):
   ```
   pg_dump --no-owner --no-acl -Fc "$RAILWAY_DATABASE_URL" -f sharesend.dump
   pg_restore --no-owner --no-acl --clean --if-exists -d "$RENDER_DATABASE_URL" sharesend.dump
   ```
   If the Render agent has already started and run migrations, `--clean` replaces those tables with the dumped ones.
3. **Use the same `VAULT_PRIVATE_KEY` and `VAULT_ADDRESS`.** A different key is a different vault, and the existing funds stay behind.
4. **Check the copy** before switching: gift counts and statuses match, and `/agent` on the Render agent shows the proof of holdings as OK.
5. **Never run both agents with jobs on against the same vault.** Only one of Railway and Render should have `JOBS=on` and `AUTO_EXECUTE=true` at a time.

With no gifts in flight, you can skip the copy and start fresh.

## 3. Before turning on `LIVE_TRADING`

- **Region.** Open `https://<agent>/health`. `region` should be `singapore`. The agent must not run in a region Binance refuses.
- **Binance API key IP whitelist.** The key only accepts listed IPs. Open `https://<agent>/egress-ip` to see what the agent calls out from, and compare it with the outbound IPs Render lists for Singapore (in the dashboard, under the service's **Connect** menu). Those addresses are shared by all your services in that region. Add them to the key on Binance.
- **Agentic Wallet sign-in.** The saved session doesn't move between machines. With `ADMIN_TOKEN` in your local `.env`, run `npm run cli -- admin signin https://<agent>`, open the link, and confirm the pairing code. It's stored on the disk, so redeploys keep it. Check `/agent` shows the session as connected.
- **Privy.** In the Privy dashboard, add the web app's new URL to the allowed origins, or email sign-in fails.
- **Test the whole path** with `LIVE_TRADING=false` first (dry run), then a $1 gift live.

## 4. After the switch

- Update `AGENT_PUBLIC_URL` consistently: it is what the agent's on-chain ERC-8004 profile points to, so if the URL changed, re-run the identity update (`agent/cli/identity.ts`).
- Update the README, demo links and `.env.example` mentions of `railway.app`.
- Keep Railway paused (not deleted) for a few days as a rollback. To go back, turn jobs on there and off on Render.

## Things to know

- **Redeploys briefly take the agent offline.** A service with a disk can't do zero-downtime deploys.
- **Config is in git.** Editing a plain `value` in the dashboard is overwritten the next time the Blueprint syncs; edit `render.yaml` instead. `sync: false` variables are only ever set in the dashboard.
- **Disk backups.** Render snapshots the disk daily and keeps seven days. The Agentic Wallet session is easy to recreate; the ledger is in Postgres, so check Render's Postgres backup options for your plan and take a manual `pg_dump` before risky changes.
